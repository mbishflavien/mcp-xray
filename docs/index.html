One less thing to watch.

mcp-xray calls every tool on your MCP server with the inputs that break things, sandboxed, so nothing it finds can turn around and touch your team.

It watches. You don't have to.

It asks what's there.

Every tool, resource and prompt the server advertises, listed before anything is touched.

Then it tries to break it.

Type confusion, oversized strings, null bytes, injection strings, built straight from the tool's own schema.

It actually calls the tool.

Not a simulation. The real tool, on the real server, gated so a destructive one can't run without you saying so.

It writes down what happened.

A clean rejection, a silent crash, a hang. Each one scored, with the evidence attached.

Built for servers you don't trust.

Schema-aware fuzzing

Mutations come from each tool's own declared schema, not a guess: type confusion, oversized strings, path traversal, null bytes, SQL, shell and template injection, mass assignment, missing required fields.

Destructive-tool gate

A keyword policy blocks calling anything named like delete, drop, destroy, purge or wipe, unless you explicitly allow it.

delete_all_records
skipped_unsafe: blocked by default

Sandboxed execution

Every probe runs inside a WASI sandbox with no filesystem, network or environment access, and a hard limit on both time and memory.

sandbox limits
timeout 30s · memory 16MiB

Bounded by design

A hostile schema can't make the scan grow without end: mutation counts, evidence length and listed tools are all capped.

caps
fields ≤ 200 · evidence ≤ 2000B · tools ≤ 10,000

CI-ready reports

Text for a person, JSON for a pipeline, SARIF for GitHub code scanning. Pick the severity that fails your build:

--fail-on
exit code: 1

Honest by default

A healthy rejection is not a finding. No padded severity, no inflated counts. Just what actually happened.

greet
info sql_injection: rejected, not reported
