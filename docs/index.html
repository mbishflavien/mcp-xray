Open source · Go · MCP security

See through your MCP server before something else does.

mcp-xray connects to a Model Context Protocol server, generates adversarial inputs from each tool's own schema, and actually calls the tool with them — then scores what really happens. Its probes run sandboxed, so a malicious or compromised server can't turn a scan against the thing scanning it.

Why it's different

Most scanners fuzz the server. mcp-xray sandboxes itself.

The server you're scanning might be exactly the thing you don't trust yet. A scanner that assumes otherwise is a liability.

Typical MCP scanner

  • Generates payloads in the host process
  • Sends them straight to the live server
  • A crafted schema can hang or crash the scanner itself
  • No limit on how much the target can make it do

mcp-xray

  • Payload generation runs inside a WASI sandbox — no filesystem, network, or environment access
  • Every probe run has a hard timeout and a memory cap
  • An adversarial schema's mutation count is capped, not unbounded
  • Calling a destructive-looking tool needs an explicit --allow-tool
How it works

Introspect, fuzz, call, score.

01

Introspect

Connect over stdio and list every tool, resource, and prompt the server advertises.

02

Generate

Build adversarial payloads from each tool's own input schema — type confusion, oversized strings, path traversal, null bytes, SQL/shell/template injection, mass assignment, missing required fields.

03

Call, for real

Actually invoke the tool with each payload, gated by a safety policy that blocks anything that looks destructive unless you say otherwise.

04

Classify & score

A healthy rejection, a silently accepted invalid input, an internal error, a hang, or a crash — each becomes a severity-scored finding with evidence.

05

Report

Text for a human, JSON for a pipeline, or SARIF for GitHub code scanning — with --fail-on to gate CI on severity.

Proof, not a promise

The safety gate, caught in the act of working.

A tool named delete_all_records — every one of its eight mutation attempts blocked before a real call was ever made.

mcp-xray --allow-tool delete_all_records -- ./example-server
# without --allow-tool: 8/8 blocked, 0 real calls made
[info] delete_all_records: sql_injection: skipped_unsafe
[info] delete_all_records: mass_assignment: skipped_unsafe
    ... 6 more, all skipped_unsafe

# with --allow-tool delete_all_records: the gate lifts, real calls happen
[low]  delete_all_records: sql_injection: accepted_invalid
[low]  delete_all_records: mass_assignment: accepted_invalid
What's inside

Built like something meant to run against things you don't trust.

Schema-aware fuzzing

Mutations are derived from each tool's declared schema, not guessed blind.

type_confusionoversized_stringpath_traversalnull_bytesql/shell/template

Destructive-tool gate

A keyword policy blocks calling anything named like delete, drop, destroy, purge, or wipe — unless explicitly allowed.

Bounded by design

Sandboxed probes, a 16MiB memory cap, a hard execution deadline, capped mutation counts, capped evidence length, capped pagination.

CI-ready reports

Text, JSON, or SARIF for GitHub code scanning, with --fail-on <severity> to gate a pipeline on what's found.
